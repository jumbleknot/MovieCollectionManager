# Doc drift: the doc-impact sweep and the quarterly audit

V17 keeps each `openwiki/` summary in step with its **source document**. Nothing mechanical keeps
the source document in step with **the code it describes**. This runbook covers the docs-from-code
direction. For wiki-from-docs, see [wiki-maintenance.md](wiki-maintenance.md).

The design and its evidence are in
[docs/proposals/PRD-DocDriftPrevention.md](../proposals/PRD-DocDriftPrevention.md). The
specification is [specs/101-doc-drift-prevention/](../../specs/101-doc-drift-prevention/spec.md).

| Layer | When | What it is | Status |
|---|---|---|---|
| 1. Doc-impact sweep | every SDD feature, at `/speckit-tasks` and at close-out | a required task in the project's tasks template: search the docs for every identifier the feature changes | **live** (feature 101) |
| 2. Mechanical per-PR check | every PR | `describes:` front matter on runbooks plus a guardrail | **not built**; it is triggered by SM-3 below |
| 3. Drift audit | quarterly | one session reads the procedure docs against the tree | **live**, procedure below |

## The doc-impact sweep (layer 1)

Every `tasks.md` generated by `/speckit-tasks` carries a **Doc-impact sweep** task in Phase 1 and a
**Close-out re-search** task in the Polish phase. They come from the project override
`.specify/templates/overrides/tasks-template.md`, which Spec Kit resolves ahead of its own core
template. The constitution (v2.10.0, **Documentation**) makes the sweep mandatory even when the
template is not used. The final validation checklist carries the close-out step.

The search is literal and cheap on purpose:

```bash
git grep -n -F "<term>" -- '*.md' ':!specs/' ':!docs/proposals/' ':!docs/decisions/'
```

Each hit becomes a named doc task, or gets a one-line reason it needs no change. Dated records
("measured on …", incident logs, version history) are history, so they need no change. Feature
020's five-month miss would have been one search for `--profile audit`.

## The quarterly drift audit (layer 3)

The audit measures whether layer 1 works. It is a backlog item that files its own successor, so the
cadence needs no scheduler and no standing owner. The session that closes one audit opens the next.

**Scope**: every doc that states current procedure: `docs/runbooks/**`, `docs/MCM-Architecture.md`,
Part 1 of `docs/MCM-Learnings.md`, and the project READMEs under `agents/`, `mcp-servers/`, `infrastructure-as-code/` and `frontend/`. **Not**: ADRs (`docs/decisions/`), `specs/`, `docs/proposals/`, or dated records inside
any doc ("measured on …", incident tables, version history). Those describe the past and stay as
written.

**Procedure**:

1. **Work from a worktree**, per AGENTS.md. Note the commit you read against.
2. **Read in chunks by area**: dev and test runbooks plus architecture and READMEs; the dev container
   and CI diagnostics; Renovate, wiki and scanning; production and homelab. One chunk at a time keeps
   each read against the tree honest.
3. **Verify only checkable claims** against the tree: file and directory paths, commands, nx
   `project:target` names, script names and flags, environment variables, compose service,
   container, volume, network, stack and profile names, ports, workflow and job names, versions and
   pins, and links.
4. **Edit only what is proven wrong**, with the smallest edit that makes it true, and cite the
   evidence in the commit. Prefer citing the pin file to restating a version.
5. **Report what cannot be proven**, for example claims about the live host, the forge or upstream
   tools. List them in the PR as suspected drift rather than editing.
6. **Code comments** found stale are out of the docs' scope. File them as one backlog item (as item
   #1022 was).
7. **Refresh the wiki in the same PR**: `node scripts/wiki-refresh.mjs --stale`, then `--diff`,
   edit, `--record` for each page listed (the [wiki-refresh skill](../../.claude/skills/wiki-refresh/SKILL.md)).
8. **Record the measure** in the audit log below: lines read, proven drift fixed, and the rate per
   1,000 lines. SM-2 expects the rate to fall from one audit to the next.
9. **Refresh [MCM-Learnings.md](../MCM-Learnings.md)** in the same PR. On `main`, run
   `node scripts/count-repo-metrics.mjs` and append its column to the measurement log (Part 3)
   unchanged, never editing an earlier column. Update a ledger line's status (Part 2) only if a
   lesson changed, and rewrite Part 1 only where this audit proved it wrong. The document's own
   "How to update this document" section has the rules for each part.
10. **Check SM-3**: would a `describes:` link have caught any of the drift, on a feature whose sweep
    ran? If so, layer 1 is not enough. File layer 2 as a `status/needs-spec` item.
11. **File the next audit, then close this one.** Use `node scripts/backlog.mjs create`, title
    `Drift audit YYYY-MM (quarterly, layer 3 of doc-drift prevention)` about three months on, with
    labels `type/chore` and `priority/p2`, and this procedure as its acceptance criteria. Then
    close the current item.
