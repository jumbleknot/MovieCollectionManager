# Doc drift: the doc-impact sweep, Spec Kit upgrades, and the quarterly audit

V17 keeps each `openwiki/` summary in step with its **source document**. Nothing mechanical keeps
the source document in step with **the code it describes**. This runbook covers the docs-from-code
direction. For wiki-from-docs, see [wiki-maintenance.md](wiki-maintenance.md).

The design and its evidence are in
[docs/proposals/PRD-DocDriftPrevention.md](../proposals/PRD-DocDriftPrevention.md). The
specification is [specs/101-doc-drift-prevention/](../../specs/101-doc-drift-prevention/spec.md).

| Layer | When | What it is | Status |
|---|---|---|---|
| 1. Doc-impact sweep | every SDD feature, at `/speckit-tasks` and at close-out | a required task in the project's tasks template: search the docs for every identifier the feature changes | **live** (feature 101) |
| 2. Mechanical per-PR check | every PR | `describes:` front matter on runbooks plus a guardrail | **not built**; it is triggered by SM-3 below |
| 3. Drift audit | quarterly | one session reads the procedure docs against the tree | **live**, procedure below |

## The doc-impact sweep (layer 1)

Every `tasks.md` generated by `/speckit-tasks` carries a **Doc-impact sweep** task in Phase 1 and a
**Close-out re-search** task in the Polish phase. They come from the project override
`.specify/templates/overrides/tasks-template.md`, which Spec Kit resolves ahead of its own core
template. The constitution (v2.10.0, **Documentation**) makes the sweep mandatory even when the
template is not used. The final validation checklist carries the close-out step.

The search is literal and cheap on purpose:

```bash
git grep -n -F "<term>" -- '*.md' ':!specs/' ':!docs/proposals/' ':!docs/decisions/'
```

Each hit becomes a named doc task, or gets a one-line reason it needs no change. Dated records
("measured on …", incident logs, version history) are history, so they need no change. Feature
020's five-month miss would have been one search for `--profile audit`.

## Upgrading Spec Kit

The project override is a **fork** of Spec Kit's core tasks template. After an upgrade, the core
template may have improved, and `/speckit-tasks` would keep using the old copy without saying so.
`scripts/check-speckit-overrides.mjs` (a guardrails step) turns that into a red check. The override's
first line records the fork point:

```text
<!-- forked-from: .specify/templates/tasks-template.md sha256=<hash> spec-kit=<version> -->
```

The procedure, all in one PR:

1. **Run the upgrade.** Install the new CLI release as in
   [dev-environment-setup.md](dev-environment-setup.md), then run
   `specify integration upgrade claude --force` from a worktree. It rewrites the files listed in
   `.specify/integrations/*.manifest.json`, but not `overrides/`, the constitution or `openwiki/`.
   Bump `SPECKIT_VERSION` in `.devcontainer/toolchain.Dockerfile` and the version in
   dev-environment-setup.md to the same release, so the dev container's CLI matches the files.
   **Before** `--force`, find the manifest files carrying deliberate local edits. `specify
   integration status` counts them, but on a Windows checkout most of its count is CRLF-only.
   Compare each file's committed LF bytes, and the same bytes as CRLF, against the manifest hash.
   A file that matches neither is a real edit. Re-apply it after the upgrade. In the 0.11.2 → 0.16.5
   upgrade the only one was `.claude/skills/speckit-taskstoissues/SKILL.md` (Forgejo `backlog.mjs`
   fan-out instead of GitHub MCP, feature 049).
2. **Run the gate**: `node scripts/check-speckit-overrides.mjs`. Expect `core-changed` if the
   upgrade touched the core tasks template. The failure prints the core template's diff since the
   fork base, found by hash in git history. In a shallow clone it says history is unavailable and
   still fails. Compare the two files by hand in that case.
3. **Merge the upstream change into the override.** Keep the **Doc-impact sweep** and
   **Close-out re-search** tasks and the `EXCEPTION` note in the sample-task comment.
4. **Record**: `node scripts/check-speckit-overrides.mjs --record`. Never hand-type the hash. The
   gate refuses to record an override that has lost the sweep task.
5. **Re-run the gate** (expect ✓) and its tests:
   `node --test scripts/__tests__/check-speckit-overrides.test.mjs`.

The other failure codes:

| Code | Meaning | Fix |
|---|---|---|
| `override-missing` | The override file is gone | Restore it from git, then `--record` |
| `header-invalid` | Line 1 is not a fork point | `--record` rewrites it |
| `sweep-missing` | No task line carries `**Doc-impact sweep**` | Restore the task. `--record` refuses until you do |
| `resolution-broken` | `setup-tasks.ps1` no longer calls `Resolve-Template` (the path, `TASKS_TEMPLATE`) and `Resolve-TemplateContent` (the content, `TASKS_TEMPLATE_CONTENT`, which `/speckit-tasks` prefers since 0.16) for `tasks-template`, or either no longer checks `overrides/` first. A bare `return $null` before the check (template-name validation) is allowed | Spec Kit changed how it resolves templates. Re-evaluate where the sweep must live (proposal §4.2: a preset, or composition), then update the guard at the cause. **Never delete the guard** to make it pass |

**Known gaps** (from feature 101's own sweep):

- The **Copilot** integration's tasks agent (`.github/agents/speckit.tasks.agent.md`) reads the core
  template directly, not through `Resolve-Template`, so it never sees the override. Only the
  constitution rule covers a Copilot-generated `tasks.md`. The file is Spec Kit-owned, so it is not
  edited here.
- `/speckit-constitution` checks the **core** tasks template for consistency after an amendment.
  When amending the constitution, check the override too.

## The quarterly drift audit (layer 3)

The audit measures whether layer 1 works. It is a backlog item that files its own successor, so the
cadence needs no scheduler and no standing owner. The session that closes one audit opens the next.

**Scope**: every doc that states current procedure: `docs/runbooks/**`, `docs/MCM-Architecture.md`,
and the project READMEs under `agents/`, `mcp-servers/`, `infrastructure-as-code/` and `frontend/`. **Not**: ADRs (`docs/decisions/`), `specs/`, `docs/proposals/`, or dated records inside
any doc ("measured on …", incident tables, version history). Those describe the past and stay as
written.

**Procedure**:

1. **Work from a worktree**, per CLAUDE.md. Note the commit you read against.
2. **Read in chunks by area**: dev and test runbooks plus architecture and READMEs; the dev container
   and CI diagnostics; Renovate, wiki and scanning; production and homelab. One chunk at a time keeps
   each read against the tree honest.
3. **Verify only checkable claims** against the tree: file and directory paths, commands, nx
   `project:target` names, script names and flags, environment variables, compose service,
   container, volume, network, stack and profile names, ports, workflow and job names, versions and
   pins, and links.
4. **Edit only what is proven wrong**, with the smallest edit that makes it true, and cite the
   evidence in the commit. Prefer citing the pin file to restating a version.
5. **Report what cannot be proven**, for example claims about the live host, the forge or upstream
   tools. List them in the PR as suspected drift rather than editing.
6. **Code comments** found stale are out of the docs' scope. File them as one backlog item (as item
   #1022 was).
7. **Refresh the wiki in the same PR**: `node scripts/wiki-refresh.mjs --stale`, then `--diff`,
   edit, `--record` for each page listed (the [wiki-refresh skill](../../.claude/skills/wiki-refresh/SKILL.md)).
8. **Record the measure** in the audit log below: lines read, proven drift fixed, and the rate per
   1,000 lines. SM-2 expects the rate to fall from one audit to the next.
9. **Check SM-3**: would a `describes:` link have caught any of the drift, on a feature whose sweep
   ran? If so, layer 1 is not enough. File layer 2 as a `status/needs-spec` item.
10. **File the next audit, then close this one.** Use `node scripts/backlog.mjs create`, title
    `Drift audit YYYY-MM (quarterly, layer 3 of doc-drift prevention)` about three months on, with
    labels `type/chore` and `priority/p2`, and this procedure as its acceptance criteria. Then
    close the current item.
