# Per-user collection backups — operating manual

**Feature 073** (backlog item #236). Per-user scheduled and on-demand backups of movie
collections to storage the *user* owns — S3-compatible or WebDAV — with versioning, keep-last-N
retention, and a restore that only ever creates new collections.

This is the operator's view: what to set, what breaks, and how to tell which. The design
reasoning is in [specs/073-scheduled-backups/](../../specs/073-scheduled-backups/).

---

## What is different about this feature

Three properties shape everything below, and each is the reason for a decision that otherwise
looks odd.

**The credentials belong to the user, not to us.** A destination is storage the user owns and
pays for. We hold their S3 secret or WebDAV app password sealed with AES-256-GCM, and we never
return it, log it, or echo it in an error. Two consequences an operator will meet: a probe
failure can only ever say *which kind* of failure it was, never what the server replied; and
**account deletion does not delete the user's artifacts**. Those objects are their property at
storage they control — removing them would be destroying the data we were trusted to copy.

**An unattended run acts as the user.** There is no service account, no admin path and no
broader-privileged fallback (FR-024). A scheduled run mints the user's own access token from a
Keycloak **offline token** they granted by explicit consent. If that grant is gone, the run
**fails** — it does not find another way to read the data.

**The BFF's Mongo is standalone.** No replica set, therefore no multi-document transactions.
Exactly-once scheduling rests on a single-document atomic claim, not a transaction. The Redis
leader lock beside it is an optimisation with a TTL guess in it and is *not* the guarantee.

## Configuration

| Variable | Default | What it does |
|---|---|---|
| `BACKUP_CREDENTIAL_ENC_KEY` | — | AES-256-GCM master key for destination secrets and offline tokens. **Separate from `AGENT_CONFIG_ENC_KEY`** so the blast radius is not widened. Rotating it orphans every stored secret. |
| `BACKUP_TICK_SECRET` | — | Guards the internal tick route. **Unset disables the scheduler**, announced once at boot. |
| `BACKUP_TICK_INTERVAL_MS` | `60000` | How often `server.js` calls the tick. |
| `BACKUP_TICK_ALLOW_TIME_OVERRIDE` | unset | Permits `?now=` on the tick. **Dev and CI only** — never set in production. |
| `BACKUP_ALLOWED_DESTINATION_HOSTS` | — | Comma-separated allow-list for destination hosts. |
| `BACKUP_MAX_MOVIES` | `25000` | Run ceiling, by count. |
| `BACKUP_MAX_UNCOMPRESSED_BYTES` | `67108864` | Run ceiling, by size (64 MiB). |

Dev and CI values are generated by `scripts/gen-dev-env.mjs` and `scripts/gen-ci-env.mjs`. Both
seed `BACKUP_CREDENTIAL_ENC_KEY` rather than syncing it: a re-run must not orphan existing
secrets.

### The size ceiling is deliberate, and it fails loudly

A run holds the whole artifact in memory, because a stream that fails half way leaves a partial
object the user later discovers is unrestorable *at the moment they need it*. The ceiling is
what makes that trade defensible. Past it the run fails with a message naming both the limit and
the measured value — raise `BACKUP_MAX_MOVIES` / `BACKUP_MAX_UNCOMPRESSED_BYTES` rather than
guessing. Streaming is a filed follow-up, not an oversight.

## The scheduler

`server.js` runs a `setInterval` that POSTs to `/bff-api/backups/tick` over **127.0.0.1**, with
the secret. That loopback hop is not a workaround: `server.js` is CommonJS *outside* the Metro
bundle and cannot import `src/bff-server/*` at all. It also keeps the tick callable by a cron
sidecar later, should the timer ever move out of the app.

**NO TICK FIRES UNDER `pnpm start`.** `server.js` does not run under Metro. That is expected, not
a fault to chase — in dev, call the tick route directly.

### Is it actually ticking?

The tick is silent when nothing is due, by design: a log line a minute saying "nothing happened"
is a log nobody reads. To confirm it is alive, look for the first Mongo connect after boot — the
tick is the only thing that touches Mongo on an idle server:

```bash
docker logs mcm-bff-service-nonsecure 2>&1 | grep -aE 'listening|scheduler|mongo_connect'
```

Expect `backup scheduler ticking every 60000ms` at boot and a `mongo_connect` line one interval
later. Measured 2026-09-21: container up at 23:52:33.295, tick-driven connect at 23:53:33.831.

### Triage

| Symptom | Cause to check first |
|---|---|
| `backup scheduler disabled` at boot | `BACKUP_TICK_SECRET` unset. |
| Tick returns **404** | Wrong secret — the route 404s rather than 401s so it does not advertise itself. Check the BFF and caller hold the *same* value. |
| Tick returns 400 "Time override not permitted" | `?now=` without `BACKUP_TICK_ALLOW_TIME_OVERRIDE=1`. Correct in production. |
| `leader: false` | **Normal.** Another instance took the lock. Not an error. |
| A job never runs | Is `nextRunAt` set? A disabled job has none by design, so re-enabling does not fire for an occurrence that passed while it was off. |
| A job is stuck | `claimedAt` set by an instance that died. It self-heals after the 30-minute reclaim ceiling. |

## The standing permission (offline token)

Enabling a schedule requires a **separate OIDC round trip** carrying `scope=openid
offline_access`. The result is stored, never turned into a session.

Two operational facts:

- **The consent callback must be a registered redirect URI on every origin the app is served
  from.** The BFF derives it from the request it arrived on, so `:8081`, `:8082` and `:8443`
  each need registering. `/bff-api/auth/init` registers the current one; the realm JSON carries
  the rest.
- **The user needs the `offline_access` realm role.** Keycloak grants it through the realm's
  default-roles composite, so Admin-API-created users inherit it. Users imported from realm JSON
  **do not** unless the import says so — this is how the seeded `e2e-test-user` ended up unable
  to consent, with the failure surfacing as a blank page after sign-in.

Disabling the last schedule, deleting the job, or deleting the account **revokes the token at
Keycloak**, in that order: revoke first, forget second. Reversed, a failed revocation strands a
live, non-expiring token with nothing left pointing at it.

To confirm a revocation really happened, use the token — do not read our database:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  "$KEYCLOAK_URL/realms/$KEYCLOAK_REALM/protocol/openid-connect/token" \
  -d grant_type=refresh_token -d "client_id=$KEYCLOAK_CLIENT_ID" \
  -d "client_secret=$KEYCLOAK_CLIENT_SECRET" -d "refresh_token=$TOKEN"
# 400 invalid_grant ("Offline user session not found") = genuinely revoked
```

## Retention

"List the keys, sort them, delete the tail." Artifact keys end in an ISO-8601 timestamp, which
sorts lexicographically in the same order it sorts chronologically, so the destination's own key
ordering *is* the age ordering.

Three consequences worth knowing:

- **A failed run prunes nothing.** Not a detail — it is the safety property. Pruning on the
  failure path turns "today's backup did not happen" into "and yesterday's is gone too".
  `partial` counts as not-successful for the same reason.
- **A failed prune needs no retry state.** The object is still there, so the next successful run
  lists it and tries again. Nothing is queued and nothing can drift.
- **A prune failure never fails the run** (FR-027). It is recorded in `pruneFailureReason`,
  separately from `failureReason`, because the backup the user asked for did happen.

Only keys matching `<basePath>/<jobId>/<iso>.json.gz` are ever deletion candidates. Files the
user keeps at the same destination are never touched, even inside the job's own folder.

## Running the tests

Bring the destinations up first — they are in their own compose file:

```bash
docker compose -p mcm --env-file infrastructure-as-code/docker/stacks/mcm.env \
  -f infrastructure-as-code/docker/backups/compose.yaml up -d
```

```bash
MCM_REQUIRE_BACKUP_TARGETS=1 MCM_REQUIRE_LIVE_STACK=1 pnpm nx test:integration mcm-app
```

**Set both flags.** Without them a missing destination makes the suites *skip*, and a skip reads
as a pass. **Watch the skip count, not just the exit code.**

Web E2E runs in the official Playwright image — chromium cannot be installed in the dev
container. The recipe, including the worktree trap (the bind mount silently yields an
almost-empty directory), is in
[devcontainer.md](devcontainer.md). `BACKUP_TICK_SECRET` and the `BACKUP_TEST_*` values live in
`.env.local`, which Playwright does **not** load — pass them explicitly.

**Verify the container is running the image you just built** before believing any E2E result:

```bash
[ "$(docker inspect -f '{{.Image}}' mcm-bff-service-nonsecure)" \
  = "$(docker inspect -f '{{.Id}}' mcm-bff:latest)" ] && echo match || echo STALE
```

This caught two full E2E runs in this feature's development that were diagnosing a stale
container rather than the code.

## Audit events

Eleven events (FR-035): destination created / updated / tested / deleted, schedule enabled /
disabled, run started / succeeded / failed, restore started / completed / refused. Each carries
counts, sizes and identifiers only.

The sink strips every key containing `token` plus an explicit redact list. **That rule does not
cover `secretEnc`, `accessKeyId` or a destination password** — none contains "token" — so those
are kept out by construction and asserted in `backup-audit.integration.test.ts` against the real
secret values rather than assumed.

A leak scan over a full flow is the honest check:

```bash
docker logs mcm-bff-service-nonsecure > /tmp/bff-backups.log
grep -cF "$BACKUP_TEST_S3_SECRET_KEY" /tmp/bff-backups.log   # expect 0
```

Grep for the secret **values**, not the field names: a log that never prints the word
`secretAccessKey` can still print the key itself.

## Known gaps

- **No account-deletion path exists in the app.** `tearDownUserBackups(userId)` is written,
  tested and ready; nothing calls it, because there is no route, no `deleteUser` in
  `keycloak.ts`, and nothing outside the E2E teardown helper. Whoever builds account deletion
  must call it.
- **Streaming snapshots** are not implemented; the size ceiling stands in for them.
- **Failure notification is in-app only.** No email — `email-service.ts` only triggers Keycloak
  account flows, so this would mean building a real outbound channel.
